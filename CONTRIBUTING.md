# Contribution and review guide

This repository is a portfolio case study. Changes should improve clarity, implementability, traceability, or testability rather than simply increase document length.

## Review checklist

- Is each normative requirement clear about who acts, what they do, and when?
- Is there a defined approval path, exception route, or escalation path where needed?
- Can an independent reviewer identify evidence that demonstrates operation?
- Are targets clearly distinguished from legal obligations, contractual commitments, and measured performance?
- Are framework mappings stated as indicative and checked against the cited version?
- Are secrets, personal information, customer data, and internal contact details excluded from examples?
- Does a proposed change preserve the fictional/portfolio-only disclaimer?

## Change workflow

1. Make a focused change in Markdown, CSV, or a template.
2. Check links, spelling, date/version metadata, and internal references.
3. Update the evidence register, risk register, control mapping, and test plan if the requirement changes.
4. Record the reason for material changes in the pull request or commit description.
5. For a real deployment, obtain review by appropriate security, legal/privacy, HR, IT, business, and data owners. A GitHub merge does not count as corporate policy approval.
